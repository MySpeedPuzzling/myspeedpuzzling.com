# Puzzle catalogue

Loaded automatically when you read or edit files of this area (puzzle names and codes, approvals and moderation, brands, the barcode scanner, filters and SEO of puzzle pages). Read on purpose when planning work here before touching code. Each entry is the as-built summary; its doc under `docs/features/` is the design of record - read it before changing behaviour, and update both when behaviour changes.

- **Puzzle names, EANs and brand codes**: `docs/features/puzzle-names/` (README = design of record, `implementation-plan.md` = phases; phase 1a shipped the storage, phase 1b switched search to the keys, phase 1c dropped the old single column, phase 2 shows the names, phase 3 edits them, phase 5 the codes) — `puzzle.alternative_names` (jsonb list `[{name, language}]`, value object `PuzzleNames`), `name_language`, `names_changed_at`, and two search keys `search_names` / `search_codes` (`PuzzleSearchKeys`, one line per folded name / `e:` EAN / `c:` brand code). **Names and codes change only through `Puzzle` methods** - `changeNames()` (cleans, drops names folding equal to the main title or each other, moves `names_changed_at` only on a real change) and `updateProductIdentifiers()`; the entity maintains both keys with the one PHP fold `SearchText::fold()` - no triggers, no SQL folding, raw SQL never writes names or codes. Bump `SearchText::VERSION` and run `myspeedpuzzling:rebuild-puzzle-search-keys` whenever the fold or the key format changes (`--dry-run --report=<csv>` first; nightly on lily with `--alert-on-drift` = warning when a key was stale) (also once after the release that adds keys, and after a puzzle inserted by SQL - the Ravensburger Puzzle Month runbook; hidden puzzles stay secret through `hide_until`, not through empty keys). The old single `alternative_name` column is gone (stopped in phase 1c-1, dropped in 1c-2) - `LegacyAlternativeNameCoverageTest` fails on the word anywhere in `src/`, `templates/`, `assets/` outside its allowlist; `PuzzleNames::legacyAlternativeName()` (first Czech name, else the first) remains only for API v1 `alternative_name` (and the internal API merge queue's `alternativeName`). Every names form (moderator edit, approval queue, change-request review, merge review, "Suggest a change") is the names editor (`PuzzleNamesType` + `puzzle/_names_editor.html.twig`); full-record forms carry a `PuzzleRecordVersion` and refuse a stale save (`PuzzleChangedMeanwhile`, 422); messages changing a puzzle are `SerializedByLock` on `PuzzleRecordVersion::lockKey()`; change requests apply names as a diff; merges keep every name of every merged puzzle (`union()`: survivor's names, merged puzzles' other names, their main titles, the survivor's previous main title). Decision/merge snapshots hold `alternativeNames` + `nameLanguage`, older ones an `alternativeName` string - `PuzzleHistoryChange` reads both. **Every puzzle text search goes through `PuzzleTextSearch` / `PuzzleSearchQuery`** (`condition()` + `score()` for the 6 best-match tiers, barcode lookups through `barcodeCondition()` - exact, leading zeros tolerated), never ILIKE on puzzle columns; paged sorts end on the puzzle id (ties straddle pages). **Showing names:** the lines under a main title come from one partial `puzzle/_name.html.twig` (second line = the name in the viewer's language, `PuzzleNameLanguage::forViewer()`: page language, on `/en/` a signed-in player's country language via `CountryLanguage`; "Matched: …" in search results) - lists, pickers, the add recap and the puzzle page; every other surface, e-mails and share images show the main title only. What crawlers read (title, meta description, JSON-LD) follows `forPage()` - the page language, never the viewer. **Codes:** `EanList` / `BrandCodeList` are the one parser of the stored `ean` / `identification_number` strings and of the forms' inputs - lists with `", "`, each code once: a barcode (GTIN with a right check digit) as digits without leading zeros, **any other EAN-field value exactly as typed** (catalogue numbers, typos, junk with letters - never "cleaned"), brand codes upper case; `updateProductIdentifiers(EanList, BrandCodeList)` stores `toStored()` of a list only when it differs from the stored one (`equals()`), so writers passing codes on never rewrite them. Every form has one input per code (`CodeListType` + `puzzle/_code_inputs.html.twig`, "+ another" on the label line), no comma field - except the add form, which shows one EAN and one brand code input (a box carries one of each; other editions come through suggestions); pages show `display()` (a UPC with its 12th digit) through the Twig `puzzle_eans()` / `puzzle_brand_codes()`. The field is called **Brand code** in every locale; the add form's "What is it?" link on both code labels opens `puzzle/_codes_help_modal.html.twig` (per-locale photo `public/img/puzzle-codes/box-side.{locale}.webp`, generator in `docs/features/puzzle-names/codes-help/`; a changed photo needs a new file name). A brand code is found typed with or without the EAN check digit some brands print after it: `BrandCodeCheckDigit::aliases()` = extra `c:` lines + the picker's search field (`codes-help-and-check-digit.md`). `myspeedpuzzling:canonicalize-puzzle-codes` (dry run unless `--write`, which needs `--undo=<csv>`; `--report=<csv>`) writes format-only changes and reports the rest for change proposals.
- **Puzzle approvals**: `docs/features/puzzle-approvals.md` — queue `/admin/puzzle-approvals` (admins + moderators, `PUZZLE_MODERATION_ACCESS`) for `puzzle.approved = false`. **No reject** (new puzzles carry solving times): approve with corrections (`ApprovePuzzle`), or merge into the duplicate via the existing merge review (moderator = reporter, `?return=` back; the survivor inherits approval). New brand → `PuzzleApprovalBrandChoice` approve / use existing / merge into an approved brand (moves all its puzzles + change-request proposals as objects, deletes the duplicate). **Every catalogue decision (change/merge approve+reject, puzzle/brand approval, brand merge, a moderator's direct edit) writes an append-only `puzzle_moderation_decision` row** via `PuzzleModerationDecisionRecorder` in the deciding handler — no FKs, decider id/name/code copied, so it outlives requests, puzzles and players; a new decision type must record there too (and gets a line in `GetPuzzleHistory`). **Outdated requests close by themselves** (`OutdatedPuzzleRequests`, status `outdated`, tab "Already done", no decider, reporter not told): a merge request with < 2 puzzles left (reported ids resolve through `puzzle_redirect` - `MergeRequestPuzzles`; the review/approval/internal API use the puzzles as they are now), a change request whose puzzle has every proposed value - closed by the merge / record save that did it, daily `myspeedpuzzling:close-outdated-puzzle-requests` as the safety net (warning = something went around). A merge **moves** the merged puzzle's change requests onto the survivor (`puzzleMergedInto()`, FK no longer cascades); `PuzzleMergeForeignKeyCoverageTest` lists every FK to `puzzle` with what a merge does with it. **Box-text mismatches** `/admin/box-text-mismatches` (own access_control rule above `^/admin`): what the box says (`box_text` analysis: pieces, EAN via `EanList`, brand code via `BrandCodeList`, brand) and the catalogue does not, from the daily `myspeedpuzzling:detect-box-text-mismatches` - never a change proposal, moderators edit or Dismiss (`box_text_mismatch_decision` per puzzle, field, value). Read-only per-puzzle history at `/admin/puzzles/{id}/history`; moderators edit any puzzle directly at `/admin/puzzles/{id}/edit` ("Edit puzzle" on the puzzle page). A puzzle's record (every name - main title, its language and the other names, all in the names editor - brand, pieces, codes, image) is written by `PuzzleRecordUpdater` only - change request approvals and direct edits; validate-first, returns the before/after snapshots **A new puzzle always comes with a photo of its box** — `AddPuzzle::$puzzlePhoto` is non-nullable, `PuzzleBoxPhoto::constraint()` is the one rule (add form + multiscan quick-add; only competition-round puzzles may lack one, see competitions docs, and an admin's `AddApprovedPuzzle` through the internal API)
- **Duplicate brands**: `docs/features/brand-duplicates.md` — why the same brand exists several times (free-text brand in the add form always created one, other players' unapproved brands were hidden from the picker, brands with only approved puzzles never reach the queue). Since 2026-10-03 every brand picker lists **every** brand (`GetManufacturers::allIncludingUnapproved()`; public filters + admin pages keep approved-only) and a typed brand name goes through `ManufacturerResolver` (the one place, `AddPuzzleHandler` + `AddPuzzleToCompetitionRoundHandler`): equal after trim + collapsed whitespace + lowercase = that brand (approved first, then most puzzles, then oldest), nothing more normalised, no unique index yet; the picker JS matches the plain `name`, exact or a single prefix match. `ManufacturerMerger` is the **one** brand merge (approval queue + internal API): moves puzzles + change-request proposals, unions EAN prefixes, keeps logo/approval, the merged slug becomes a `manufacturer_slug_redirect` (301 on every brand route via `ManufacturerSlugRedirectSubscriber`, never re-used by `GenerateManufacturerSlug`), one `brand_merged` decision per merged brand. Survey 2026-10-03 (99 certain groups) + hardening plan in the doc
- **Community moderators**: `docs/features/community-moderators.md` — non-admin role (`player.moderator_since`, null = none) that reviews the puzzle catalogue (change + merge requests, puzzle approvals, direct puzzle edits + history) and reaches nothing else under `/admin`. `PuzzleModerationVoter` (`PUZZLE_MODERATION_ACCESS` = admin OR moderator); the access_control rule `^/admin/puzzle(s/|-((change|merge)-requests|approvals))` must stay above `^/admin`. - **Barcode scanner**: `docs/features/barcode-scanner/README.md` — research + staged plan (2026-10-05). `barcode_scanner_controller.js` (multiscan, add-time form, global search) uses the browser's own `BarcodeDetector` where it reads EAN-13 (Google's engine on Android; zbar only loaded where needed) and zbar elsewhere. zbar-only on Android (2026-10-04) cost ~half of the Android scans: Chrome opens the highest-index back lens at 640×480, and zbar has a low blur tolerance. Google's engine sometimes returns another valid code (`4005555…` → `0045555…`), contained by `Value\EanList`. **Camera fixes shipped together on 2026-10-13 (Jan's call, no A/B)** - README §5.6: 1080p asked, Android re-picks "camera 0, facing back" (remembered in `localStorage`), 1.5× default zoom (the player's choice remembered), continuous focus + refocus kick (tap, or 2.5 s without a code), torch, zbar decodes a centred band at full resolution (4 agreeing reads, 8 for `0…`/EAN-8; native keeps 10), the HUD partial `_barcode_scanner_hud.html.twig` (z-index above the video - the zoom pill sat behind it before) and the `?scan-debug=1` overlay (only while in the URL, never remembered) to ask players for a screenshot; `?scanner=zbar|native` forces one decoder while in the URL for testing. Step 1 shipped 2026-10-18: a scanned code starting with 0 that is not found finds the puzzle of the one catalogue code it is a parity misread of (`FindPuzzlesByScannedEan` + `EanParityMisread`; add form, multiscan, "Report duplicate" - API v1 and `FindPuzzlesByExactEan` stay exact), and every camera session reports itself to `POST /-/scan-session` (`ScanSessionController`, log channel `barcode_scanner`, count in Loki). **Both readers side by side on Android since 2026-10-19** (README §5.7, Vanja's S25 test): Google's reader on the whole frame + zbar on the band in the same session, each in its own loop, zbar within a time budget that keeps Google's reader at its own pace (`HelperBudget`: a mid-range phone's Google reader went 83 → 418 ms a frame when both shared one loop), the rule in `assets/barcode_acceptance.js` (zbar by its iPhone rule and answering only to itself, Google's 10 reads stopped by any other code either reader saw, both agreeing twice each = accepted at once; 12-digit UPC-A forms compared as 13), `?scanner=native` = the old Google-only behaviour; zbar is served by us (`public/barcode-scanner/zbar-wasm-<version>/`, exact npm bytes, immutable via `.docker/barcode-scanner/barcode-scanner.caddyfile`, outside the service worker - a new version = a new directory, never a CACHE_VERSION bump) with jsdelivr as fallback, never two copies in one page (§5.9); the camera is released while the page is hidden and taken again when shown, a camera taken away (track `ended`) restarts ≤ 3×/min, every start gets a `<video>` made by `document.createElement` (§5.10 - an iPhone gives the camera to one page at a time, the loser kept a black picture; Safari paints no camera into a `<video>` Turbo brought from the next page's parsed HTML); every reader rests at ≤ 10 decodes/s while no code was seen for 1 s (§5.8 - decoding every frame nonstop heated an iPhone in multiscan), the overlay is redrawn only when it changes; the reports carry `accepted_by` + each reader's numbers - decide from them whether Android drops Google's reader. Still open: the own decoder (Step 4); never trust a native-only read for storing. Simulator + decoder prototype: `.claude/worktrees/barcode-research/` (local)

- **SEO (puzzle pages + sitemaps)**: `docs/features/seo/implementation-plan-2026-10.md` — puzzle meta description = facts first (solo, pairs, teams from `PuzzleSummary`), call to action, EAN last. Puzzle sitemap `lastmod` is never earlier than `GetPuzzleIdsForSitemap::PAGE_LAST_REBUILT_AT`: bump it to the deploy date only when **every** puzzle page changes its main content, title/meta, structured data or links (never for styling, never automatically - Google trusts `lastmod` only while it stays accurate). **A puzzle page's Google preview must be its own picture**: `og:image`, Product `image` and `ItemPage.primaryImageOfPage` share one URL (`page_image`), and other puzzles' pictures on a puzzle page are CSS backgrounds, never `<img>` (Google picked a related puzzle's box once; it does not index CSS images) - guarded by `testThePuzzlesOwnPictureIsTheOnlyPreviewCandidate`
- **Puzzle merges are destructive and audited:** approving deletes the merged puzzles and moves their solving times/collection/wishlist/sell-swap/lending rows onto the survivor. `ApprovePuzzleMergeRequestHandler` therefore writes a `puzzle_merge_audit` row first (full before/after snapshot + the ids of everything migrated or dropped, plus `decisionSource`/`decisionConfidence`/`decisionNote`) — for admin-UI merges too. **A puzzle may legitimately hold several EANs / catalogue numbers as a comma-separated list** (one per edition or region) — the admin UI's comma-joined pre-fill is correct, not corruption. Merges therefore *union* both records' codes (`unionIdentifiers()`, de-duplicated, survivor's first); never reduce a list to one value. It likewise carries over any cover image or manufacturer that **only** a to-be-deleted puzzle had, and keeps **every name** of every merged puzzle as an other name of the survivor (its main title too, `PuzzleNames::union()`; the survivor's previous main title stays as an other name when the reviewer picks another). **Admins can revert an audited merge of two puzzles** ("Revert this merge" on the request page, `RevertPuzzleMergeRequestHandler`, docs/features/puzzle-approvals.md "Reverting a merge"): the merged puzzle comes back under its id, the inventory's rows go back, survivor fields the merge changed are restored unless edited since; status `reverted`. A new kind of row a merge moves needs its way back there too.
