### F1 · blocker · `src/Controller/NavClickController.php:164-175`, `assets/nav_instrumentation.js:125` and `:294` · status: resolved in 62c99662 (amended P0-03)
**Problem.** Every beacon carries `page: window.location.pathname`, and the controller writes it unmasked to the `navigation` stream (stderr → Loki). Several routes carry a live credential in the path:
- `/password-reset/{token}`: `PasswordResetController` docblock: "the token is the proof", a successful reset signs the browser in, the page is served with `Referrer-Policy: no-referrer` so the token never leaks. Token valid 60 min (`ResetPasswordRequest::LIFETIME_MINUTES`).
- `/delete-account/{token}`: same comment ("the token is the proof"), 60 min (`AccountDeletionRequest::LIFETIME_MINUTES`).
- also `/{_locale}/claim-oauth2-credentials/{claimToken}` (one-time secret display), `/connect/social/{provider}/finish/{token}`, `/{_locale}/newsletter/confirm|unsubscribe/{token}…`, `/{_locale}/email-preferences/{token}`, `/{_locale}/import-event-participants/{competitionId}/{token}…`, `/{_locale}/photo-stash/{token}`.

These pages extend `base.html.twig` (`password_reset.html.twig` → `_auth_layout.html.twig`, `account_deletion_confirm.html.twig`), so `app.js` starts the instrumentation there. The worst case is the normal case. A link opened from an e-mail lands in a new tab with empty `sessionStorage`, so `sendViewportOncePerSession()` runs on module start and sends `page=/password-reset/<64-hex token>` before the visitor does anything. Any chrome click or Back/Forward line on those pages logs the token again. Today these paths do not reach Loki: the Traefik log is filtered and request logging is still only a proposal. P0-03 therefore adds a new place where credentials are stored, and it is the commit meant for production on its own. The `page()` check only rejects whitespace, `?`, `#` and control bytes.

**Fix.** Mask secrets before logging, and in the script too, so they never leave the page. Replace every path segment matching `^[0-9A-Za-z]{32,}$` with `{token}`. All the tokens above are hex or alphanumeric, ≥ 32 characters, with no dash. UUIDs and slugs contain dashes and stay as they are. Do it in `NavClickController::page()`, the authoritative place, and mirror it in `nav_instrumentation.js`. Add a `droppedBeacons`-style controller test that asserts `/en/password-reset/<64 hex>` is logged as `/en/password-reset/{token}`, plus a node scenario for the viewport line on such a page. A route-name meta would be an alternative, but masking keeps "path only" from the requirement. Before deploying, grep the router (`debug:router`) for any other `{…token…}`, `{hash}` or `{signature}` path parameter.

### F2 · minor · `src/Controller/NavClickController.php:28` and `:170` · status: resolved in 62c99662 (amended P0-03)
**Problem.** The server and the script disagree on what a well-formed `data-nav` is. Without the `D` modifier, PCRE `$` also matches before a trailing newline. Proof: `php -r 'var_dump(preg_match("~^[a-z_]+/[a-z_]+/[a-z0-9_]+$~", "footer/learn/faq\n"));'` returns `int(1)`, while the JS pattern returns `false` for the same string. The server therefore logs `item: "faq\n"`, a value the script can never send. The JSON formatter escapes it, so this is not line injection. `testTheScriptAndTheServerAcceptTheSameValues` claims parity but does not test this case: its "space" case uses a trailing space, which `$` does not skip. `page` likewise accepts any non-ASCII text, `<`, `"` and similar, up to 300 bytes. `location.pathname` never produces such characters, because it is percent-encoded ASCII. The endpoint can therefore be fed arbitrary free text that the script cannot produce, against the check "cannot be abused to write arbitrary log content".

**Fix.** `NAV_PATTERN = '~^[a-z_]+/[a-z_]+/[a-z0-9_]+\z~'` (or add `D`). Restrict `page` to RFC 3986 path characters: `~\A/[A-Za-z0-9\-._\~%!$&'()*+,;=:@/]*\z~`. Add `"footer/learn/faq\n"` to `malformedValues()` and to `droppedBeacons()`, plus a `page` with `<script>` and one with a raw non-ASCII character.

### F3 · minor · `src/Services/SentryTracesSampler.php:46` and `:56` (interaction with `/-/nav-click`) · status: resolved in 62c99662 (amended P0-03)
**Problem.**
- **Tracing volume.** Tracing is enabled (`config/packages/sentry.php`) and the sampler runs for every main request, so every beacon (one per chrome click) becomes a Sentry transaction at `SENTRY_TRACES_SAMPLE_RATE`. Until now `/-/` beacons were rare. This one is sent on every click and can multiply transaction volume and quota use.
- **Session reads.** For a signed-in visitor, the beacon carries the session cookie, and the sendBeacon cookies cannot be omitted. The sampler then calls `$request->getSession()`, because `TracingRequestListener` runs at kernel.request priority 4, after `SessionListener`. When `PROFILING_TRIGGER_SECRET` is set, it also calls `$session->get(...)`, which starts the session: one `sessions` read per click, and at most an hourly metadata write.
- **Tests miss both.** The endpoint tests cannot see either effect, because tracing is off in `test`.

This contradicts "no cookies/session" in production only.

**Fix.** At the top of the sampler closure, return `0.0` for the telemetry beacons before anything touches the session, for example `if (str_starts_with($request->getPathInfo(), '/-/')) { return 0.0; }`. The health checks already live under `/-/`. Add a unit test for the sampler.

### F4 · minor · `tests/Controller/NavClickControllerTest.php:179-189` · status: resolved in 62c99662 (amended P0-03)
**Problem.** `testTheBeaconNeverTouchesTheSession` sets a `PHPSESSID` cookie. In `test`, the session storage is `session.storage.factory.mock_file`, whose cookie name is `MOCKSESSID` (`vendor/symfony/framework-bundle/Resources/config/session.php:64`). The request is therefore just another guest request: `hasPreviousSession()` is false, and the test proves nothing about a signed-in visitor's beacon, which is what its docblock claims.

**Fix.** Sign in with `TestingLogin::asPlayer($browser, PlayerFixture::PLAYER_REGULAR)` and make one GET to establish the session. Then POST the beacon and assert three things: no `Set-Cookie`, `$browser->getRequest()->hasSession() === false || $browser->getRequest()->getSession()->isStarted() === false`, and exactly one log record.

### F5 · minor · `tests/Navigation/NavigationViewer.php:42` and `:56` · status: resolved in f6dfd77c
**Problem.** The "member" viewer, `PLAYER_WITH_STRIPE` (`created_events: true`), is also an event owner: it created organizations and competitions (`OrganizationFixture`). `GetCompetitionPermissions` treats `added_by_player_id` as owner rights, and so does the "You organize" logic. So the member row is "member + organiser", and only the "player" row is role-free. This does not change any P0-02 pin. It does make later per-role checks ambiguous, because they reuse `NavigationViewer`. MENU-02 expects "member ≈ 56, +1 organiser", MENU-01 "an organiser fixture shows Events you organize", and the chrome budget compares member with organiser: a member here will already show the organiser row and pay its cost.

**Fix.** Pick one:
- Add a role-pure member: `PLAYER_PRIVATE` plus a membership created in the test, rolled back by DAMA like the moderator grant, with a `ROLE_FACTS` row `created_events: false`.
- Keep the fixture, but state in `baseline.md` §1 and in the `MEMBER` constant's comment that member = member + event owner, so MENU-02 records its numbers knowingly.

**P0-03, endpoint**
- Single-action controller, POST only (GET → 405), always 204.
- Body read at most 1 KB + 1 from the stream; JSON object with `v: 1`, depth ≤ 4.
- `k` restricted to an allow-list; every enum field (layout, bucket, pointer, via, dir) checked strictly; booleans checked with `=== true`; unknown values become `null`/`unknown` or drop the line.
- Exactly one `info` line per accepted beacon. No user agent, IP or referrer is logged: no WebProcessor is configured, only `PsrLogMessageProcessor`.
- Stateless firewall pattern is exact (`/-/nav-click$` inside `^(…)`, tested against `/-/nav-click-other`), `security: false`. No subscriber sets a cookie on this route: the sliding cookie needs a user token, the referral cookie needs `?ref=`. F3 is the only production session touch.

The breadcrumb handler still sees it, like `service_worker`, but runtime contexts are isolated per request, so nothing leaks into another request's event. Its own JSON stderr handler is at `info`. `TurboDriveFormResponseSubscriber` ignores the beacon (no turbo-stream Accept, 204).

**P0-03, script**
- Delegated capture listener on `document`, registered once per document. It matches only `a[data-nav], button[data-nav]` via `closest()`, drops values outside the pattern or over 100 characters, and dispatches a bubbling `msp:nav` with `{surface, place, item}`.
- GA `nav_click` is sent only when `gaLoaded === true` and `gtag` is a function.
- The viewport bucket is sent once per tab session (`sessionStorage`; nothing is sent when storage is missing or throws). Pointer type and the phone/desktop tier use the Conventions query.
- Back/Forward is counted exactly once:
  - Turbo restore: counted in `turboRestore()`. The following `location.href` load is a same-URL `replace`, so it is not counted again; the orchestrator's WebDriver check confirmed one line.
  - Cross-document traverse: counted from `navigation.activation`, falling back to Navigation Timing `back_forward`.
  - bfcache restore: counted on `pageshow.persisted`.
  - `hasUAVisualTransition` is taken from the navigate or popstate event.
- Every browser API use is guarded: no `sendBeacon`, no `sessionStorage`, no Navigation API, no `matchMedia`, or a throwing listener cannot break a click. The body is a string, so it is sent as `text/plain` with no CORS preflight, and the service worker leaves the POST alone.
- The commit is self-contained: it cherry-picks cleanly onto `origin/main`, references no P0-02 file, adds no translation keys, and the state row records `b49d3c8d` as "deploy separately".
